## Goal
Below a mobile breakpoint, `NavBar.vue` collapses its nav links (New job/Jobs/CVs) behind a
hamburger toggle instead of showing them inline, and the "AI Recruiting" wordmark shrinks to
just its `Sparkles` icon. At and above that breakpoint, nothing changes from today.

## Scope
In scope:
- `frontend/src/components/NavBar.vue`: a hamburger toggle button (mobile-only), a
  `mobileMenuOpen` ref, and the "AI Recruiting" text wrapped in its own element so it can be
  hidden independently of the icon next to it. Selecting a nav link or clicking outside the open
  panel closes it (mirrors the existing Settings-menu close-on-select/click-outside pattern
  already in this file).
- `frontend/src/styles/cmps/navbar.css`: the actual responsive behavior lives here as a plain
  `@media` block, not as Tailwind `hidden`/`md:flex` utility classes on `.navbar-links` — see
  Open Question 1 for why.
- Tests: `frontend/tests/NavBar.test.ts` — the hamburger button, the wrapped brand-text element,
  and the open/close toggle behavior (click opens, clicking a link or the outside overlay
  closes) exist and behave correctly at the DOM/class level. See Risks for what this can't prove.

Out of scope:
- Any change to what the nav links are, where they go, or their per-role visibility
  (`v-if="user?.role !== 'candidate'"` etc.) — only how they're presented below the breakpoint.
- The Settings gear menu and the theme toggle in `.navbar-actions` — unaffected, stay visible
  and unchanged at every viewport width.
- Any other page's own responsive behavior — this task is `NavBar.vue` only.

## Assumptions
- Frontend-only, pure CSS/template change — no backend, no `stack:full` override needed.
- **Why the responsive rule is plain CSS, not a Tailwind `hidden md:flex` utility on
  `.navbar-links`:** `.navbar-links` already has a `display: flex` declaration in
  `navbar.css`, which is plain, unlayered CSS (imported via `main.css`'s
  `@import './styles/cmps/index.css'` chain, outside any Tailwind `@layer` block). Per CSS
  cascade-layer rules, unlayered CSS always wins over Tailwind's layered utility classes
  regardless of specificity or breakpoint variant — this exact trap silently broke a Tailwind
  padding utility earlier this session (`.plan/013-2026-08-10-job-search-filter.md`'s
  icon-overlap fix, `pl-9` vs `pl-9!`). Adding `hidden md:flex` to an element `.navbar-links`
  already styles would be silently overridden by the existing unlayered rule the same way.
  Writing the breakpoint logic directly in `navbar.css` avoids the trap entirely instead of
  reaching for `!`-important-modified utilities on every affected class.

## Open Questions
1. **Which breakpoint?** **Recommended:** Tailwind's standard `md` boundary, 768px
   (`@media (max-width: 767px)` for the mobile-only rules) — this app already uses Tailwind's
   default scale elsewhere (e.g. `sm:p-8` in `App.vue`), so reusing the same `md` cutoff keeps
   "mobile" meaning the same width everywhere rather than introducing a second, bespoke
   breakpoint value.
2. **Does selecting a nav link auto-close the open mobile menu?** Not doing so would leave the
   panel open over the newly-navigated page until the user taps the hamburger again.
   **Recommended:** yes — each `RouterLink` gets a `@click="closeMobileMenu"` alongside its
   existing navigation, the same closes-on-select behavior the Settings menu already has for
   "User settings"/"Logout".
3. **Does clicking outside the open panel close it?** **Recommended:** yes, reusing the exact
   `<div v-if="menuOpen" class="fixed inset-0 z-20" @click="closeMenu" />` overlay technique
   already implemented for the Settings dropdown in this same file — proven pattern, no new
   interaction model to invent.

Proceeding with the recommended answers on all three unless told otherwise.

## Steps
1. **`NavBar.vue` script**: add `const mobileMenuOpen = ref(false)`,
   `toggleMobileMenu`/`closeMobileMenu` functions (mirroring the existing
   `toggleMenu`/`closeMenu` for the Settings dropdown), import `Menu`/`X` from `@lucide/vue` for
   the hamburger's open/closed icon (this app already swaps `Sun`/`Moon` and already imports `X`
   for the CV-preview close button elsewhere, so this icon-swap-on-state pattern is established).
2. **`NavBar.vue` template**:
   - Wrap the "AI Recruiting" text node in `<span class="navbar-brand-text">AI Recruiting</span>`
     (the `Sparkles` icon stays a direct, unwrapped sibling — always visible).
   - Add a hamburger `<button class="navbar-hamburger" type="button" :aria-expanded="mobileMenuOpen" :aria-label="mobileMenuOpen ? 'Close menu' : 'Open menu'" @click="toggleMobileMenu">` with `X`/`Menu` swapped on `mobileMenuOpen`, placed between the brand link and `.navbar-links`.
   - `.navbar-links` gets `:class="{ 'is-open': mobileMenuOpen }"`; each `RouterLink` inside it
     gets `@click="closeMobileMenu"` added to its existing attributes.
   - Add the click-outside overlay (`<div v-if="mobileMenuOpen" class="fixed inset-0 z-20" @click="closeMobileMenu" />`) per Open Question 3 — note this is a second, independent overlay from the Settings menu's own (different z-index layering isn't a concern since only one of the two menus is ever meaningfully open in the same interaction, but keep them as separate `v-if` blocks, not shared state).
3. **`navbar.css`**:
   - `.navbar-hamburger`: same visual treatment as `.theme-toggle` (`display: none` by default —
     desktop never shows it).
   - `@media (max-width: 767px) { ... }` block (per Open Question 1) containing:
     - `.navbar-hamburger { display: inline-flex; ... }` (visible on mobile).
     - `.navbar-brand-text { display: none; }` (icon-only brand on mobile).
     - `.navbar-links { display: none; position: absolute; top: 100%; left: 0; right: 0; flex-direction: column; align-items: stretch; padding: 0.75rem 1.5rem; background: var(--surface); border-bottom: 1px solid var(--border); box-shadow: var(--shadow-card-md); }` and `.navbar-links.is-open { display: flex; }` — a dropdown panel instead of today's inline row, only when open.
   - No changes to `.navbar-links`'s base (non-mobile) rule — desktop keeps exactly today's
     inline-row layout.
4. **Tests**: per Scope's Tests bullet above — assert the hamburger exists and toggles
   `aria-expanded`/the open class; assert `.navbar-links` gets `is-open` on click and loses it on
   a link click or the outside-overlay click; assert `.navbar-brand-text` wraps "AI Recruiting"
   (confirming the icon and text are now independently targetable, without asserting the CSS
   itself — jsdom can't evaluate a `@media` query, see Risks).

## Validation
- `cd frontend && npx vitest run` and `npx vue-tsc --noEmit` — 100% pass, clean.
- `npx vite build` and grep the built CSS for the new `@media (max-width: 767px)` block and its
  three rules, same verification technique used for prior CSS-only changes this session (confirms
  the rules actually compiled, since jsdom can't render them).
- Manual check via the `run` skill, resizing the browser (or using devtools' device toolbar)
  across the 768px boundary: above it, nav links show inline and the full wordmark is visible,
  exactly as today; below it, only the icon shows next to "AI Recruiting"'s hidden text, a
  hamburger appears, tapping it opens a dropdown with the same links, selecting a link or tapping
  outside closes it.

## Risks
- jsdom does not evaluate CSS or `@media` queries, so no automated test can prove the visual
  breakpoint behavior itself — only that the DOM structure and JS-driven open/close state are
  correct. The `vite build` CSS grep plus the manual resize check are the only real verification
  for the visual part, same limitation as every other CSS-only change this session.
- Reusing the exact click-outside-overlay pattern the Settings menu already uses keeps this
  low-risk — no new interaction model, just the same one applied to a second menu.
