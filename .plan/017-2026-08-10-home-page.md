## Goal
A new home page explains the product (what it is, who it's for, what problem it solves, how it
works, what to do next) and becomes the landing page for every authenticated role after login —
today Admin/Recruiter land on the job-creation form and Candidate lands on the jobs list, with
no shared "what is this app" surface at all. "AI Recruiting" in the header becomes a real link
to this page, with the pointer cursor that implies.

## Scope
In scope:
- `frontend/src/pages/HomePage.vue` (new): three sections — "What it does" (folds in *what is
  this application*, *who is it for*, *what problem does it solve* into one concise intro,
  since the backlog's 3-section structure doesn't give each question its own section), "How it
  works" (the analyze → match → score → explain loop, per `.doc/product-definition.md`'s
  Product Vision), and "Key features" (an icon list). A fourth, non-"section" element answers
  the backlog's fifth question ("what should I do next?"): a role-aware row of action links —
  see Open Question 2.
- `frontend/src/router/index.ts`: `/` now renders `HomePage` instead of `JobPage`. `JobPage`
  moves to `/jobs/new` (see Open Question 1 for the path choice). The `beforeEach` guard's
  Candidate-away-from-`/` redirect is removed (home is no longer role-gated — that's the
  entire point) and replaced with a Candidate-away-from-`/jobs/new` redirect to `/jobs`,
  mirroring the existing pattern already used for the Recruiter-away-from-`/cvs` redirect.
- `frontend/src/components/NavBar.vue`: "AI Recruiting" becomes a `RouterLink` to `/` again —
  reversing `.plan/014-2026-08-10-ui-ux-polish.md`'s specific decision to make it non-interactive,
  which was correct *at the time* because `/` wasn't a meaningful destination; it is now. The
  "New job" link's `to` changes from `/` to `/jobs/new`, and its active-state check changes from
  `route.name === 'job'` to match the renamed route (see Open Question 1).
- `frontend/src/pages/JobsListPage.vue`: the empty-state "Create a job" CTA's `to` changes from
  `/` to `/jobs/new`.
- Tests: `frontend/tests/router.test.ts` — `/` renders the home page for every role with no
  redirect; `/jobs/new` still redirects Candidate to `/jobs` and is reachable for Admin/Recruiter;
  login/signup still land on `/` and see the home page regardless of role.
  `frontend/tests/NavBar.test.ts` — the brand mark is a real link to `/` with the expected active
  state on the home route; the "New job" link points to `/jobs/new`.
  `frontend/tests/HomePage.test.ts` (new) — all three sections render with non-empty content; the
  action row renders the correct links for each role (Admin, Recruiter, Candidate).
  `frontend/tests/JobsListPage.test.ts` — the "Create a job" CTA points to `/jobs/new`.

Out of scope:
- Any change to `JobPage.vue`/`JobForm.vue`'s own content or behavior — only its route path
  moves, per Open Question 1.
- A public (pre-login) marketing page — this home page is only ever reached by an authenticated
  user; an unauthenticated visit to `/` still redirects to `/login` via the existing
  `!isAuthenticated` guard clause, which runs before any of this plan's new logic.
- Redesigning the app's overall content-width container (`App.vue`'s `max-w-2xl` wrapper around
  `RouterView`) — see Open Question 3.

## Assumptions
- Frontend-only — no backend involved, this is routing and a new static content page.
- The backlog's "3 sections" and its 5 questions aren't a 1:1 mapping; "who is it for" and "what
  problem does it solve" read naturally as part of the same introductory section as "what is
  this application," not as two more standalone sections the backlog didn't actually ask for.

## Open Questions
1. **Where does the job-creation form move to?** It needs a path since `/` is taken by the new
   home page. **Recommended:** `/jobs/new`, mirroring the already-established `/jobs` (list) —
   a natural nested action under the existing jobs area, matching how `/api/job` (singular,
   per `.claude/rules/naming.md`) already models the domain. Route `name` becomes `job-new`
   (from `job`), and every `to="/"`/`route.name === 'job'` reference in the frontend updates
   with it (`NavBar.vue`'s "New job" link and active-state check, `JobsListPage.vue`'s "Create a
   job" CTA).
2. **What does the role-aware "what should I do next" row actually link to, per role?**
   **Recommended:**
   - Admin: "Post a job" (`/jobs/new`) and "View jobs" (`/jobs`) — full access to both.
   - Recruiter: "Post a job" (`/jobs/new`) and "View jobs" (`/jobs`) — same as Admin for this
     row; Recruiter's CVs route is already hidden entirely per
     `.plan/015-2026-08-10-hide-cvs-route-recruiter.md`, so no CV-related CTA for this role.
   - Candidate: "Browse jobs" (`/jobs`) and "Upload a CV" (`/cvs`) — Candidate can't create jobs,
     so no "Post a job" link; Candidate's CVs access is unchanged and still the primary
     CV-related destination.
   This reuses existing routes only — no new destinations, no new capability implied that the
   role doesn't already have.
3. **Should the home page use a wider layout than the rest of the app's `max-w-2xl` content
   column?** A three-section explainer with an icon grid often reads better wider than 672px,
   but changing `App.vue`'s global wrapper to be route-conditional is more invasive than this
   task needs. **Recommended:** keep the existing `max-w-2xl` wrapper unchanged — stack the
   three sections and the action row vertically within it, consistent with every other page's
   width, and revisit only if it visually reads as cramped once built (a call better made
   looking at the actual rendered page than guessed here).

Proceeding with the recommended answers on all three unless told otherwise.

## Steps
1. **`frontend/src/pages/HomePage.vue`** (new): three `<section class="card ...">` blocks (or
   similar, matching this app's existing card-based section styling) —
   - "What it does": 2-3 sentences covering purpose (candidate uploads a CV, it's matched
     against a job description via an LLM, producing a score + explanation), audience
     (recruiters/hiring managers primary, candidates secondary — per
     `.doc/product-definition.md`'s Target Users), and the problem it solves (manual resume
     screening is slow and inconsistent; keyword ATS tools are shallow).
   - "How it works": the analyze → match → score → explain loop as a short numbered/ordered
     list or step sequence.
   - "Key features": an icon list (`@lucide/vue`, reusing existing icon choices for existing
     concepts per `.claude/rules/ui-and-styling.md` — `Briefcase` for job postings, `FileText`
     for CV upload/analysis, `Sparkles` for AI-powered matching/scoring already used as the
     brand icon, plus one new icon for role-based access, e.g. `ShieldCheck`, since this app has
     none yet for that concept).
   - A role-aware action row per Open Question 2's answer, using `useAuth()`'s `user.value.role`.
2. **`frontend/src/router/index.ts`**: swap `{ path: '/', name: 'job', component: JobPage }` for
   `{ path: '/', name: 'home', component: HomePage }` and add
   `{ path: '/jobs/new', name: 'job-new', component: JobPage }`. In `beforeEach`, remove the
   `user.value?.role === 'candidate' && to.path === '/'` branch and add a
   `user.value?.role === 'candidate' && to.path === '/jobs/new'` branch redirecting to `/jobs`,
   in the same position/style as the existing Recruiter-`/cvs` branch.
3. **`NavBar.vue`**: brand mark reverts from `<span class="navbar-brand">` to
   `<RouterLink to="/" class="navbar-brand" :class="{ 'is-active': route.name === 'home' }">`
   (drop the `.plan/014` comment explaining why it was a `<span>` — that reasoning no longer
   applies now that `/` has a real destination). "New job" link's `to` becomes `/jobs/new`, its
   active-state check becomes `route.name === 'job-new'`.
4. **`JobsListPage.vue`**: the "Create a job" CTA's `to` becomes `/jobs/new`.
5. **Tests**: per Scope's Tests bullet above.
6. **Docs**: update `.doc/architecture.md`'s router route table and `NavBar.vue`/`JobPage.vue`
   component descriptions, plus a Change Log entry.

## Risks
- Renaming the `job` route to `job-new` and moving its path is a small breaking change for
  anyone with `/` bookmarked expecting the job-creation form — acceptable, this app has no
  external users yet and the backlog explicitly asks for this landing-page change.
- The role-aware action row (Open Question 2) is the one piece of this plan with actual
  per-role logic to get right — worth explicit test coverage per role, not just a visual check.
