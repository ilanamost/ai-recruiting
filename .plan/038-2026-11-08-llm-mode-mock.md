## Goal
Let the backend run end to end without an LLM provider. Setting `LLM_MODE=mock` in the
backend `.env` makes resume analysis and match scoring return deterministic, locally computed
results instead of calling the Anthropic API. Backlog task: "Support a LLM_MODE=mock .env
variable, so that analysis and scoring will work without an LLM model as well."

## Scope
Task is `stack:full` (confirmed 2026-11-08), but it is almost entirely backend.

**Backend (`backend/`):**
- New `backend/src/lib/llm-mode.ts`: `isMockMode()` reads `process.env.LLM_MODE`
  (`'mock'` → true; unset or `'live'` → false).
- `backend/src/scoring/index.ts`: `scoreMatch` short-circuits to a mock scorer in mock mode.
  Same `ScoreResult` shape, same 0–100 clamp.
- `backend/src/analysis/index.ts`: `analyzeResume` short-circuits to a mock analyzer in mock
  mode. Output goes through the existing `normalizeSkills` / `normalizeYearsExperience`.
- Mock logic lives in new files beside each module (`scoring/mock.ts`, `analysis/mock.ts`),
  so the real LLM path is untouched and the "narrow single module" rule still holds.
- `backend/.env.example`, `.env.staging.example`, `.env.production.example`: document
  `LLM_MODE` (production example says `live`).
- Docs: `.doc/backend-overview.md` (env var table, LLM section), `.doc/deployment.md`,
  `.doc/glossary.md` only if a new shared term is introduced.

**Frontend (`frontend/`):** no change. The API contract does not change, so
`.orchestrate/api-contract.yaml` is unchanged. See Open Question 2.

**Out of scope:** per-request mode switching, a UI toggle, mocking the Anthropic SDK at HTTP
level, changing the scoring prompt or schema.

## Assumptions
- `ANTHROPIC_API_KEY` is not needed in mock mode. No code path should construct
  `new Anthropic()` in mock mode.
- Mock results need to be plausible and stable, not smart: same inputs give the same output.
- Mock matches are persisted like real ones (immutable `match` rows), and are distinguishable
  from real ones only by their explanation text.
- Unset `LLM_MODE` keeps today's behavior (live).

## Open Questions
1. **How should the mock score be computed?**
   - **Option A (recommended): keyword overlap.** Tokenize the job description and resume,
     score = share of distinct job keywords found in the resume, scaled to 0–100 and clamped.
     Explanation names the matched and missing keywords, so it is "resume-grounded" as the
     product definition requires.
   - Option B: a fixed score (e.g. 75) with canned text. Simplest, but every match looks
     identical and ranking/star/filter features cannot be exercised.
2. **Does the frontend need to show that mock mode is on?**
   - **Recommended: no UI change.** The mock explanation text starts with `[Mock]`, which is
     visible in the match dialog. The Frontend Agent and Frontend ticket are skipped.
   - Alternative: add a banner. That needs a new API field, which changes the contract.
3. **What should an invalid `LLM_MODE` value (e.g. `LLM_MODE=mok`) do?**
   - **Recommended: fail fast at startup** with a clear error, so a typo cannot silently send
     real LLM calls.
   - Alternative: treat anything other than `mock` as live.
4. **How should mock analysis find skills?**
   - **Recommended:** years from `N years` phrases and dated ranges in the text, null when
     none (matches the "null means unclassified" rule); skills from a built-in list of common
     tech terms found in the text.
   - Alternative: always return `years_experience: null, skills: []`. Simpler, but the
     recruiter experience and skill filters cannot be exercised in mock mode.

**Answers (2026-11-08):** Q1 → keyword overlap. Q2 → no UI change (Frontend Agent and
Frontend ticket skipped). Q3 → fail fast at startup. Q4 → heuristic from text.

**Revised (2026-11-08, after manual testing):** Q3 changed. An invalid `LLM_MODE` no longer stops
the server (that crashed the frontend, which could not reach the API). The server logs the problem,
keeps running, answers `POST /api/match` with `503 service_unavailable`, and stores uploaded CVs
unclassified. The frontend now survives an unreachable API: the session check resolves to signed-out,
the router sends the user to `/login`, and the login page shows a "Can't reach the server" notice;
every API call turns a network failure into an `ApiError` with that message. The mock scorer was also
recalibrated against stored LLM scores (technology coverage 35% / vocabulary 65%, piecewise curve).

## Validation
QA checklist, each item provable by a test or command:
- With `LLM_MODE=mock` and `ANTHROPIC_API_KEY` empty, `scoreMatch` returns
  `{ score: integer 0–100, explanation: non-empty string }` and never calls the Anthropic SDK
  (assert the SDK constructor/`messages.create` mock is not called).
- `scoreMatch` is deterministic: the same job and resume text give the same result twice.
- A resume that contains the job's keywords scores higher than one that contains none.
- With `LLM_MODE=mock`, `analyzeResume` returns `years_experience` as an integer 0–60 or
  `null`, and `skills` as a normalized array (lowercase, de-duplicated, at most 30, each at
  most 50 characters). It never calls the SDK.
- A resume with no dated history gives `years_experience: null`, not 0.
- With `LLM_MODE` unset or `live`, existing scoring and analysis tests still pass unchanged.
- An invalid `LLM_MODE` value fails fast at startup (if Q3 is accepted).
- Integration (Supertest): upload a PDF CV, attach it to a job, request a match under
  `LLM_MODE=mock`. Expect 201 with a persisted match whose `explanation` is non-empty, and
  the CV list shows the mock-derived skills and experience.
- `cd backend && npm test` and the type-check pass; `.env.example` documents `LLM_MODE`.

## Risks
- Mock scores leaking into production data. Mitigation: production example sets
  `LLM_MODE=live`; docs call this out; invalid values fail fast.
- Mock logic drifting from the real result shape. Mitigation: both paths return the existing
  types and pass through the same normalizers; a shared-shape test covers both.
- The vitest config forces `ANTHROPIC_API_KEY=''`; tests must set `LLM_MODE` explicitly per
  test and restore it afterward so suites do not leak state.

## Rollout Order

3. `.env*.example` files and docs.
4. QA validation, then human approval of the QA ticket.

## Rollback
Revert the branch. The change is additive and gated by an env var, so removing `LLM_MODE`
from `.env` already restores live behavior. No schema or migration changes. Matches persisted
under mock mode stay in the database (immutable); delete them manually if unwanted.
