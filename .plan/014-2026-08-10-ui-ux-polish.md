  library.

## Open Questions
1. **What should the high-score and low-score reveal animations actually look like?**
   **Recommended:** a high score (> 80) gets a brief scale-up "pop" (0.9 → 1.05 → 1 over
   ~400ms) on the score number plus a one-cycle soft glow pulse on the score bar's fill
   (`box-shadow` pulse in `--success`, matching the existing `score-high` color) — celebratory
   but not distracting. A low score (< 50) gets a plain fade-in with no bounce/glow — i.e., the
   *absence* of the celebratory treatment is itself the differentiator, not a separate
   "negative" animation (a shake or red flash would read as scolding the candidate, which this
   product has no reason to do). A mid score keeps today's behavior (the bar's existing
   `width` transition, no new entrance animation).
2. **How to stagger the per-card entrance animation without inline styles?** A per-item
   `animation-delay` needs a value that varies with list index. `.claude/rules/ui-and-styling.md`
   says no inline styles, but this codebase already binds `:style` for genuinely dynamic,
   data-driven values (`MatchResult.vue`'s score-bar `:style="{ width: \`${match.score}%\` }"`)
   — a per-item stagger delay is the same category (computed from data, not a static override
   of what Tailwind should own), so a `:style="{ animationDelay: \`${index * 40}ms\` }"` bound
   per `<li>` is consistent with that existing precedent. **Recommended:** use that, capped at
   a handful of items (e.g. `Math.min(index, 8) * 40ms`) so a long list doesn't leave the last
   card waiting seconds to appear.
3. **Should "AI Recruiting" stop being a link entirely, or just lose the pointer cursor while
   staying a link?** The backlog phrase "since it is not clickable" reads as the reviewer's
   belief about what it *should* be, not just a request to hide the cursor on something that
   still functions as a link — `/` isn't a meaningful destination today (Admin/Recruiter's
   `/` is "New job," already reachable from the nav; Candidate is redirected straight to
   `/jobs`). **Recommended:** change the brand mark from `<RouterLink to="/">` to a plain
   non-interactive `<span>`/`<div>` — removes the pointer cursor as a side effect of removing
   the (currently redundant) navigation, rather than leaving a link that looks non-clickable,
   which would be its own small UX bug.
4. **Which token for the scrollbar color?** The backlog says "one of the theme colors light
   grey color." `--border` (`color-mix(... 35%, white)` in light mode, `--neutral-800` in dark)
   and `--border-strong` are this app's existing grey-toned chrome tokens, already used for
   subtle UI dividers/outlines — a new one-off color would duplicate an existing token for no
   reason. **Recommended:** `--border-strong` for the thumb (visible enough to grab, still
   subtle) and transparent/`--bg` for the track, in both themes — reusing existing tokens keeps
   the scrollbar in sync with any future theme-color changes instead of hardcoding a value.
5. **What's the one additional UI/UX improvement, and should it be implemented now?** Proposed:
   **empty-state and error-state cards currently pop in instantly with no transition, unlike
   the loaded content once this plan's card-entrance animation ships** — inconsistent motion
   language (everything else fades in, these don't). Suggested fix: apply the same fade-in
   treatment (no stagger, since there's only ever one such card) to the "No jobs yet"/"No CVs
   yet"/"No jobs match your filters"/error-message cards already present in
   `JobsListPage.vue`/`CvsListPage.vue`. Small, consistent with the rest of this plan's actual
   scope, low risk. **This is a suggestion only — do not implement it as part of this plan
   unless the approval response explicitly says yes to it separately from the other four
   items**, per the backlog's own instruction.

## Risks
- CSS-only entrance/reveal animations are inherently hard to unit-test meaningfully in jsdom
  (no real paint/animation timing) — tests here assert class presence and computed
  `animationDelay` values, not visual correctness; the manual check above is where the actual
  look gets verified.
- `::-webkit-scrollbar` styling has no live-DOM test coverage path in this stack (jsdom doesn't
  render scrollbars) — verified by inspecting the built CSS output (`vite build` +
  grep, same technique used in `.plan/013-...md`'s icon-overlap fix) plus the manual check.
