## Goal
Job, resume, and match data and their API calls move out of five components
(`JobsListPage.vue`, `CvsListPage.vue`, `JobCvsModal.vue`, `JobForm.vue`, `MatchResult.vue`) and
into Pinia stores. Components read state and call actions on the store; the store is the only
place that calls `lib/api.ts`, owns the resulting data, and — new behavior — turns a failed
mutation into a `vue-sonner` toast itself, instead of every component repeating its own
try/catch-and-toast block.

## Scope
In scope:
- Add `pinia` as a frontend dependency; wire `app.use(createPinia())` in `main.ts`.
- `frontend/src/stores/job.ts` (new): wraps `createJob`/`getJob`/`listJobs`/`updateJob`/
  `deleteJob`/`duplicateJob`/`listJobResumes`/`attachResumeToJob`/`detachResumeFromJob` from
  `lib/api.ts`. Owns `jobs: Job[]` and a `loadError: string | null` for the list-fetch path (see
  Open Question 2).
- `frontend/src/stores/resume.ts` (new): wraps `uploadResume`/`listResumes`/`getResumeHtmlPreview`/
  `replaceResumeFile`/`updateResume`/`deleteResume`. Owns `resumes: Resume[]` and its own
  `loadError`.
- `frontend/src/stores/match.ts` (new): wraps `createMatch`/`getMatch`/`getMatchForPair`. Thin —
  `MatchResult.vue` only ever needs one match at a time, not a list, so this store holds no
  persistent collection, just the action wrappers plus their toast-on-failure behavior.
- Every store action that mutates (create/update/delete/attach/detach/upload/replace) catches a
  failure, calls `toast.error(...)` with the same message text the component used to show, and
  re-throws so the calling component can still do its own local cleanup (e.g. closing an edit
  form only on success) — this preserves today's component-level control flow while moving the
  *notification* into the store, per the backlog's specific ask.
- Every store action that loads a list (`listJobs`, `listResumes`) sets `loadError` on failure
  instead of toasting — preserves the existing blocking "couldn't load" card UX in
  `JobsListPage.vue`/`CvsListPage.vue`, which is not a toast today and shouldn't become one (see
  Open Question 2).
- Rewrite `JobsListPage.vue`, `CvsListPage.vue`, `JobCvsModal.vue`, `JobForm.vue`,
  `MatchResult.vue` to call the new stores instead of importing `lib/api.ts` directly. Each
  component's own `try/catch { toast.error(...) }` blocks around a mutation call are removed —
  the store now does that — but a component may still need its own `catch` for anything beyond
  notification (e.g. `JobsListPage.vue`'s `confirmDelete` also updates local `resumes` cross-
  references on success today; that success-path logic stays in the component).
- Tests: every test file for the five components above needs its `vi.mock('../src/lib/api', ...)`
  approach replaced with mocking (or using a real, test-configured) Pinia store — see Open
  Question 3. New `frontend/tests/stores/{job,resume,match}.test.ts` covering each store's
  actions directly: success updates state correctly, a mutation failure toasts and re-throws,
  a list-load failure sets `loadError` and does not toast.

Out of scope:
- `lib/auth.ts` and `lib/theme.ts` — see Open Question 1 for why these stay as they are.
- `lib/api.ts` itself — stays exactly as it is, as the thin REST client layer the new stores
  call into. Stores are a layer *above* it, not a replacement for it.
- Any change to what data is fetched, when, or what the UI shows — this is a
  where-does-the-code-live refactor, not a behavior or UX change (aside from the error-path
  UX already being the same, just centralized — see the toast/loadError split above).
- Backend — nothing here touches `backend/`.

## Assumptions
- Frontend-only. No `stack:full` override needed — this is purely a frontend architecture
  change.
- "Make all the api calls happen through the store files" scopes to the five components that
  currently import `lib/api.ts` directly (confirmed via `grep -rl "from '../lib/api'"
  frontend/src` — exactly `JobsListPage.vue`, `CvsListPage.vue`, `JobCvsModal.vue`,
  `JobForm.vue`, `MatchResult.vue`). No other component calls the REST client directly today.

## Open Questions
1. **Should `lib/auth.ts` and `lib/theme.ts` also become Pinia stores?** Both already are
   centralized, reactive, module-level singletons that every consumer reads through a
   `useAuth()`/`useTheme()` composable — architecturally, they already satisfy "UI components
   call store files and these handle the api calls," just not literally via Pinia. Auth in
   particular is security-sensitive (session/cookie handling, the router guard's single source
   of truth) and touches more of the app than any other module. **Recommended: leave both as
   they are.** The backlog's actual pain point — five components each duplicating fetch calls
   and error handling — doesn't exist in `auth.ts`/`theme.ts`, which already centralize both
   concerns. Converting them would be risk (a security-relevant module, `router/index.ts`'s
   guard, and the app's theme persistence all touching the same file) for no problem this task
   is trying to solve. Revisit only if a future task specifically asks for it.
2. **Do list-load failures become toasts too, or keep today's inline blocking-error-card UX?**
   Today, `JobsListPage.vue`/`CvsListPage.vue` render a dedicated "couldn't load" card (with the
   error message) when the *initial* list fetch fails — not a toast, because the whole page has
   nothing else to show. Mutations (delete, update, attach, etc.) toast and leave the already-
   loaded list on screen. Collapsing both into "the store always toasts" would be a real UX
   regression (an unrecoverable blank page with only a passing toast, no persistent explanation).
   **Recommended:** keep the split — list-load failures set a `loadError` ref the store exposes
   (component renders it exactly as today), mutation failures toast (moved into the store, per
   the backlog). This preserves current behavior exactly; only *where the code lives* changes.
3. **How do the five components' existing tests mock the data layer once it's a Pinia store?**
   Options: (a) `vi.mock('../src/stores/job', ...)` per test file, mirroring today's
   `vi.mock('../src/lib/api', ...)` pattern almost mechanically; (b) mount components with a real
   Pinia instance (`createTestingPinia` from `@pinia/testing`) and stub/spy on actions. (a) is a
   smaller diff per test file and keeps today's mocking style; (b) is more realistic (exercises
   real store logic, including the toast-on-failure behavior, through the component) but is a
   new test dependency and a bigger rewrite. **Recommended:** (b), `@pinia/testing`'s
   `createTestingPinia` — the store's toast-on-failure behavior is itself new logic this plan
   introduces and needs its own test coverage (covered directly in
   `frontend/tests/stores/*.test.ts`, Scope above); component tests using a real/testing Pinia
   instance instead of re-mocking a fake store module avoids re-implementing store behavior
   twice (once for real, once as a hand-rolled mock) and is the standard, documented way to test
   Pinia-consuming components.

Proceeding with the recommended answers on all three unless told otherwise.

## Steps
1. **Add Pinia**: `npm install pinia` (and `npm install -D @pinia/testing` per Open Question 3)
   in `frontend/`. Wire `app.use(createPinia())` in `main.ts` alongside the existing
   `app.use(router)`.
2. **`frontend/src/stores/job.ts`**: `defineStore('job', () => { ... })` (setup-store syntax,
   matching this app's existing Composition API style throughout). State: `jobs = ref<Job[]>([])`,
   `loadError = ref<string | null>(null)`. Actions mirror `lib/api.ts`'s job functions 1:1 in
   name and signature where practical, updating `jobs` on success (e.g. `deleteJob` filters the
   deleted id out of `jobs`, `updateJob` replaces the matching entry — same logic
   `JobsListPage.vue` does inline today, moved here) and calling `toast.error(...)` + re-throwing
   on mutation failure, or setting `loadError` (not toasting) on `listJobs` failure.
3. **`frontend/src/stores/resume.ts`**: same shape for the resume domain — `resumes`,
   `loadError`, actions wrapping `uploadResume`/`listResumes`/`getResumeHtmlPreview`/
   `replaceResumeFile`/`updateResume`/`deleteResume`.
4. **`frontend/src/stores/match.ts`**: thinner — action wrappers for `createMatch`/`getMatch`/
   `getMatchForPair` with the same toast-on-failure behavior; no persistent list state.
5. **`JobsListPage.vue`**: replace the local `jobs`/`resumes`/`loading`/`error` refs and direct
   `lib/api.ts` calls with `useJobStore()`/`useResumeStore()`; `load()` becomes calling both
   stores' list actions; `filteredJobs`/`cvCount` read from `jobStore.jobs`/`resumeStore.resumes`
   instead of local refs; `saveEdit`/`confirmDelete`/`duplicate` call store actions and keep only
   their success-path local logic (e.g. closing the edit form, cross-referencing `resumes` on
   delete).
6. **`CvsListPage.vue`**: same pattern for the resume domain — local `resumes`/`loading`/`error`
   become `useResumeStore()` reads; upload/edit/replace/delete call store actions.
7. **`JobCvsModal.vue`**: the most data-heavy component — uses `useJobStore()` (attach/detach,
   `listJobResumes`), `useResumeStore()` (the "all resumes" list for the attach dropdown), and
   `useMatchStore()` (`getMatchForPair`, and indirectly `MatchResult.vue`'s own match store
   usage for create/get). Preserve the existing preview-state logic (`previewFileStatus`,
   `previewHtml`, `previewMatchId`, etc.) as component-local state — that's UI state, not server
   data, and doesn't belong in a store.
8. **`JobForm.vue`**: `createJob` call moves to `useJobStore().createJob(...)`; the component
   keeps its own local `title`/`description`/`location`/`submitting` refs (form input state, not
   server data).
9. **`MatchResult.vue`**: `createMatch`/`getMatch` calls move to `useMatchStore()`; the
   component's `loading`/`error`/`match` local state can either stay local (simplest, matches
   how `JobForm.vue`'s form state stays local) or move into the store if a future caller needs
   to observe match state from outside this component — no current caller does, so keep it local
   unless implementation reveals a reason not to.
10. **Tests**: rewrite the five components' test files per Open Question 3
    (`createTestingPinia`), add `frontend/tests/stores/{job,resume,match}.test.ts` testing each
    store's actions directly — including the toast-vs-loadError split from Open Question 2 as
    explicit test cases, not just incidentally covered.
11. **Docs**: add a short `stores/` entry to `.doc/architecture.md`'s Frontend component list,
    and a Change Log entry.

## Validation
- `cd frontend && npx vitest run` and `npx vue-tsc --noEmit` — 100% pass, clean.
- Manual check via the `run` skill: create/edit/delete/duplicate a job, attach/detach/upload/
  edit/replace/delete a CV, and score a match — every action's success/failure behavior
  (including toasts) should look identical to before this refactor; a failed initial page load
  should still show the same blocking error card, not a toast.

## Risks
- This is the largest surface-area change of any task this session by file count and touches
  every page that does real work in the app — regressions would be easy to introduce and easy
  to miss if test coverage doesn't move cleanly with the refactor. The `createTestingPinia`
  approach (Open Question 3) exists specifically to keep the existing behavioral test coverage
  meaningful rather than replaced with shallow mocks.
- Moving mutation error handling into stores changes *where* `toast.error` is called but must
  produce byte-identical toast message text to today's component-level calls, or this reads as
  an unrequested UX change. Each store action's error message should be copied verbatim from
  the component it's replacing, not rewritten.

## Rollout Order
Single frontend ticket — no backend involved. Internally, stores land before component
migration (Steps 2-4 before 5-9), since the components depend on the stores existing.

## Rollback
Revert the commits touching `frontend/package.json` (drop `pinia`/`@pinia/testing`),
`frontend/src/main.ts`, `frontend/src/stores/**` (new, delete), and the five migrated
components plus their test files. No schema/data change in this plan, so no data-migration
rollback is needed.
